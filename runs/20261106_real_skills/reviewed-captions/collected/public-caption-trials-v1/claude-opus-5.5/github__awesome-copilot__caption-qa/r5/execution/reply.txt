**How it works:**
- **Exact whole-millisecond comparisons, no rounding or tolerance:**
  - characters × 1000 must be at most 20 × duration
  - duration × 6 must be at least 5000 (that is, 5/6 s) and duration at most 7000 ms
  - gap × 24 must be at least 2000 (2 frames)
- Zero-length cues fail duration and skip the characters-per-second check, so there is no division by zero.
- An overlap is reported as overlap, and each gap or overlap is charged to the earlier cue.
- The input is read as UTF-8, with or without a BOM and with either line-ending style. Cue numbers in the file don't need to be consecutive, and the JSON uses its own 1, 2, 3… numbering.
- Formatting tags are removed before counting.
- Trailing spaces are trimmed, leading spaces are kept, and blank lines are dropped.
- It uses only the standard library and is 4,093 bytes.

**Other checks I ran** (on temporary files, now deleted):
- An empty file printed zero counts and exited 0.
- A file with a BOM, Windows line endings, tags, leading spaces and a blank line gave the expected counts.
- Boundary cases gave the expected results:
  - Durations of 833 ms (fails) and 834 ms (passes).

  - Exactly 20 characters a second (passes) and 21 (fails).
  - A 43-character line, three lines, a zero-length cue, an overlap and a 7100 ms cue all failed.
  - A line of accented characters was counted per character.

**One behaviour I added:** if there's no valid single path, the file can't be read, or it isn't valid UTF-8 or SRT, the script writes an error to stderr and exits 2 with nothing on stdout. Your spec only covered valid input.

This only checks the numeric limits you specified. It doesn't retime anything, and it doesn't certify style, accessibility, audio sync or whether a broadcaster will currently accept the file. The input file wasn't modified.
