SkillC in one minute: from intent to an extracted plan

SkillC translates a user intent into a protocol, called the extracted plan. In the LLM route, the model proposes this protocol from the user’s natural-language instructions.

User intent

“Draft the report, obtain approval, then email it.”

Correct extracted plan

draft → request_approval → send_email

Incorrect extraction

draft → send_email

The LLM proposes the plan; SkillC performs static validation against the supplied capabilities, conditions and goal. If sending requires approval, the checker can detect the skipped approval step. It does not automatically repair the plan or prove that the extraction faithfully captures every part of the user’s intent.

What is CE?

      
CE means Controlled English. It is a small, deliberately restricted language that looks like English but follows a fixed grammar. The model writes CE; SkillC parses it into a structured logic pack. CE is an output format, not a model or ordinary free-form prose.

      
Tool `send_report` (owner `agent`): requires `approved`; adds `sent`.

      
This example statement means: sending is allowed in the model only when approved is true, and a successful modeled send makes sent true.

      
What are p2g, p2g+ and p2g++?

      
They are historical prompt revision IDs: alternative instruction sheets for the same translation machinery, not different models or different CE languages.

      
RevisionWhat its instructions say

        
p2gThe original runtime-aware instructions. Bind actions to tools and required resources; ordinary thinking and writing a reply are not modeled as tool actions.

        
p2g+Allow a requested inline deliverable, such as a report written in the answer, to be an action via the built-in reply tool. Also add guidance for branch assumptions, messages versus effects, deliverable goals and separate actors.

        
p2g++Keep the plus rules, but narrow via reply to the explicitly requested final deliverable. Intermediate analysis, planning and notes must not become extra tool actions.

      

      
Why not integrate them into one?

      
They can share one implementation, and already do. _ce_runtime_sections(version=...) assembles common blocks and selects the revision-specific policy. There are not three separate compilers.

      
The older IDs remain for backward compatibility and reproducible prompt inputs. Replacing all three with one unversioned wording would silently change existing callers and invalidate comparisons with older experiments. This is a historical compatibility choice, not a claim that more versions are inherently easier to maintain or more accurate.

      
A single public default could coexist with explicitly retained historical revisions. Removing those revisions would require a deliberate migration and quality evaluation, rather than silently treating ++ as automatically better.

      
Today the low-level message builder keeps p2g as its compatibility default; the runtime-aware LLM CE path defaults to p2g+. This guide does not change those defaults or claim measured accuracy improvements for p2g++.

LLM calls: caller decision, permission gate and provider transport




During LLM compaction, this layer sends the prepared translation prompt to a model and returns its proposed text. The caller decides whether to use an LLM; this provider layer is the messenger.


  • CLI or calling application: selects deterministic extraction or model-assisted compaction.
  • Compactor: prepares the CE or JSON translation instructions and validates the returned proposal.
  • Provider layer: checks permission to make a real call, masks network addresses, sends the request and restores those addresses in returned text.


Example: A website link in the task is replaced by the temporary token [url-1]. A local lookup keeps the original address; the model sees the token, not that address.

What if no model is called?


SkillC can still parse an existing JSON/CE pack, or extract supported authored forms deterministically, and check that declaration. If the deterministic extraction does not capture enough of the task, it may return UNKNOWN; no model call does not mean automatic success. What is a placeholder?


A placeholder is a temporary text label standing in for an address, not a tool, permission or logical predicate. In this illustration, WEBSITE_LINK stands for a real website address in the original input; no actual address is displayed here.


Original task:   "Read WEBSITE_LINK and summarize it."
Text sent:      "Read [url-1] and summarize it."
Kept locally:   [url-1] means WEBSITE_LINK
Returned text:  if it contains [url-1], restore the original address


The token-to-original lookup stays in the client code; it is not sent as part of the prompt. Recognized email addresses and hostnames similarly become tokens such as [email-1] and [host-1]. Ordinary wording such as "finance team" is not replaced merely because it names a destination.


The model does not see the hidden address, and masking it does not fetch the linked document or provide its contents. This masking step is separate from translating the task into CE or JSON.


This is not full anonymization: confidential report text and other unrecognized sensitive content can remain. Opening this HTML card only displays code; it does not execute that code or contact a model.




Boundary: If a real provider call is reached without explicit opt-in, it raises ModelCallsDisabled rather than silently switching to a model-free translation. Address masking is not a general confidentiality or safety filter.






The CLI chooses deterministic or model-assisted extraction before this provider layer runs. The runtime-aware reader can also refute a missing requirement without calling a model. A selected real provider call must pass require_model_opt_in. complete selects the provider; guarded_body masks network identifiers, and restore puts their originals back into returned text.

Protocol result

May semantics, goal-only scope, solver budgets and proof limits

    
Default may semantics need some declared route; tolerant detours are allowed. Adversarial semantics additionally require success under every explicitly external choice. Goal-only scope can abstain if a failure is specific to one supplied protocol rather than all protocols over its capability context.

    
Dynamic spawning is outside the fixed finite-role fragment and yields UNKNOWN, unless an earlier structural refutation already applies. Numeric updates use SSA versions. Loop widening enlarges the reachable abstraction. Solver timeout is treated toward satisfiability, never as evidence for refutation; positive results can therefore carry uncertainty.

    
The Coq specification mechanizes theorem schemas under their hypotheses, not a full verification of the Python implementation. Intent fidelity and concrete payload faithfulness remain separate obligations.
