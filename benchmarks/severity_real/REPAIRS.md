# Repairs on the real protocols: what the analysis buys an engineer

Generated by `scripts/severity_repairs.py` from `<case>/pack.json` (deterministic, no model, no network); `tests/test_severity.py` checks that the shipped `pack_*.json` / `result_*.json` are current. kmax = 4 throughout; k* is the tolerance degree, and "k* >= 5" means no hazard is reachable within the tested budgets 0..4 (the tool reports it as null).

## Two repairs, and how they differ

**ENFORCE** moves a rule from the policy text into the tool: for every explicit guard that `PROVENANCE.md` says the source tool does not check, the guard's condition becomes a precondition (`pre`, conjoined with any existing one) of the capability it protects, exactly as the source tool code does for the rules it does enforce. Nothing else changes: every choice, branch and guard stays. **NARROW** is the tool's own repair (`skillc severity` prints it): remove the branches it names (every Catastrophic misselection) from the protocol. Narrowing removes choices, so the agent can no longer take the wrong branch at all; enforcement keeps every choice but makes the irreversible capability refuse when a rule is violated, so the wrong branch is still takeable and becomes a detour or a dead end (Benign or Futile) instead of a point of no return. In practice narrowing changes the protocol (the agent loses the ability to act on its own judgement at that node, and the engineer must know which branch is wrong), whereas enforcement changes the tool and leaves the protocol, and any agent following it, as it is. Both can only remove runs, so by the anti-monotonicity and narrowing-soundness arguments of Sections 6 and 11, hazard reachability can only shrink and k* cannot fall (asserted per case in `tests/test_severity.py`).

Conditions that change between the choice and the action are read as they hold at the action (marked *late* below). Every enforced precondition is a conjunction of atoms the pack already uses; no atom and no capability was added. Narrowing is applied context-sensitively (the protocol is unfolded along the paths the tool names) and repeated until the tool names no more branches; the number of rounds is in the table.

## What enforcing the policy-only rules buys

Of the 18 protocols, enforcing the policy-only rules raises k* above 0 for 9 (airline_cancel_reservation, airline_compensation, doc_coauthor_ship, gem_dev_team, pr_review_merge, sdlc_release_gate, sdlc_release_gate_concurrent, sdlc_release_gate_concurrent_withhold, telecom_overdue_payment_resume); 9 of them reach k* >= 5 (no hazard within the tested budgets). 9 protocols stay at k* = 0 (airline_baggage_update, airline_book_reservation, airline_change_cabin, airline_modify_flights, retail_cancel_pending_order, retail_exchange_delivered_order, retail_modify_pending_items, retail_return_delivered_order, telecom_refuel_data). 

What remains is, in every one of the 9 protocols that stay at k* = 0 and has an explicit confirmation (airline_baggage_update, airline_book_reservation, airline_change_cabin, airline_modify_flights, retail_cancel_pending_order, retail_exchange_delivered_order, retail_modify_pending_items, retail_return_delivered_order, telecom_refuel_data), the confirmation step itself: the user's answer is not a fact the tool can check, so an `execute` after a `not_yes` answer is still one misselection from the irreversible action (the hazard witness of each is `...not_yes, execute, <action>`). The nine protocols that rise are those with no confirmation step to leave behind: the three tau policies that name none (cancellation, compensation, overdue payment) and the six ProtoGuard protocols, whose skills state none. Two caveats: for the six ProtoGuard protocols the moved rule is the engineer's choice (the source role files state the condition but no tool enforces it, so the repair is a proposal about the tool, not a re-reading of existing tool code); and enforcement turns former Catastrophic branches into Futile ones (the run is stuck at the refusing tool, the goal is lost, nothing irreversible happened), so the protocol is safer, not more successful. The sensitivity table shows what closing even that would give. The engineering reading: the analysis points, per protocol, at the gates whose rule lives only in the policy text; moving those into the tool is a local code change that raises k*, and the residual k* = 0 is exactly the part that needs a different mechanism (a system-recorded confirmation, or an irreversibility window).

Narrowing, for comparison, raises k* above 0 for 18 of the 18 protocols (airline_baggage_update to >=5, airline_book_reservation to >=5, airline_cancel_reservation to >=5, airline_change_cabin to >=5, airline_compensation to >=5, airline_modify_flights to >=5, doc_coauthor_ship to >=5, gem_dev_team to >=5, pr_review_merge to >=5, retail_cancel_pending_order to >=5, retail_exchange_delivered_order to >=5, retail_modify_pending_items to >=5, retail_return_delivered_order to >=5, sdlc_release_gate to >=5, sdlc_release_gate_concurrent to >=5, sdlc_release_gate_concurrent_withhold to >=5, telecom_overdue_payment_resume to >=5, telecom_refuel_data to >=5); it removes every Catastrophic branch the tool names, including the explicit-yes `execute` branch after a `not_yes` answer, which enforcement cannot touch.
